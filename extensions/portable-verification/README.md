# Portable verification

| | |
|---|---|
| Extension | Portable verification |
| Version | 0.3.0 |
| Status | Proposal. Not part of the Standard. |
| Written against | Core v1.3, reading edition rev. 11 (tag `v1.3-rev11`), with reference files 5.2.0 (tag `ref-5.2.0`); for a signed entry and the export's seal, signatures 0.2.0 and anchoring 0.2.0, by exact version |
| Licences | This text: CC BY 4.0 ([LICENSE](../../LICENSE)). The schemas (`schemas/`) and the tests (`tests/`): Apache-2.0 ([LICENSES/Apache-2.0.txt](../../LICENSES/Apache-2.0.txt)) |

This extension says how to export sealed decision records so that someone else can check them, and how that check reports what it found. It adds two objects beside the records: an export and a verification report. It does not add a field to a decision record, and it does not change one.

Version 0.2.0 chooses the signature of a signed entry, which 0.1.0 left open: it is the [signatures](../signatures/) profile's organisation seal over the entry's identifier and digest, so that a signature cannot be moved to another entry or made under another key reference, profile or version. The export MAY also be sealed as a whole, and timestamped, by documents that travel beside it. The list of what moves, and what to do with 0.1.0 documents, is under "Changes from 0.1.0".

Version 0.3.0 changes one reading, after the review of #57: time is verified only next to a verified entry signature, the dimension and not only its signature, so a timestamp over a signature whose key's state fails gives the entry no time, as action binding 0.3.0 has it for an attachment. A report that 0.2.0 allowed is refused for it, so the version moves; see "Changes from 0.2.0".

## Scope, and what this extension does not claim

- The extension is optional. Its MUST, SHALL and SHOULD sentences bind only an implementation that says it uses portable verification 0.3.0.
- It does not change what a core field means or when it is required. Where this text and the Standard's text disagree, the Standard's text governs.
- It says nothing about what any law requires. A verification report is not a legal conclusion, and it does not grade a Conformance Level.
- The records remain input, not evidence. A seal that matches shows that the bytes have not changed since they were sealed. It does not show that the record is true, complete or lawful. A verified signature shows who issued a digest, not that what it names is any of these.
- Using this extension makes no one "certified", "compliant" or "approved".

## Core fields it reads

| Core field | In the Standard | What the extension reads it for |
|---|---|---|
| `seal_hash`, `seal_algorithm` | §5.1(3), §6.2 | The value the covered bytes are compared with; the digest an entry's signature signs |
| `affirmation_record` | §5.1(3), §6.2 | Whether the sealed bytes include it. Its timestamp and actor are the issuer's statements |
| `supersedes` | §5.1(3), §6.2 | The link to the record a correction replaces |
| `revision_history` | §6.2, §6.2.3.2 | The original seal, kept after a migration re-seals a record |
| `target_record_hash`, `target_decision_id` | §5.5, §6.2 | The seal and identifier of the record a redaction event names |
| `decision_id`, `record_type` | §6.2.1, §6.2 | Which record an export entry is; the identifier an entry's signature signs |

The export and the report refer to records. They are never inserted into one. In this text, "seal" and `seal_hash` are the Core's seal of a record; the issuer's signature of an entry is "the entry's signature" or "the organisation's seal", never "the seal".

## The export

An export made under this extension:

1. MUST identify the profile and its version (`dps-portable-verification`, `0.3.0`).
2. MUST identify, for each entry, the record (`decision_id`, `record_type`), the seal algorithm, the covered representation and any predecessor references: `supersedes`, and `target_record_hash` with `target_decision_id` for a redaction event.
3. MUST carry the covered bytes, meaning the exact bytes that were hashed into `seal_hash`, unchanged. If they are not available, it MUST say so and why.
4. MUST state how the seal field was handled when those bytes were made: either the covered bytes do not contain `seal_hash`, or they contain it with every character of its value replaced by `0`. Zeroing keeps the length of the stored value. Other placeholders, such as an empty string or null, are not covered. A seal stored in another encoding of the same 32 bytes is carried as lowercase hex. The export MUST also state whether the covered bytes include `affirmation_record`. That is a statement about the bytes, not a rule about what they must include.
5. MUST use either the original bytes or a canonical form named with a reference to a specification that fixes every byte. "Sorted JSON" and similar descriptions do not fix the bytes and are not enough.
6. MUST, for a signed entry, carry the issuer's signature as the signatures 0.2.0 organisation seal of kind `record`, in the entry's `signature` member: `algorithm` exactly `Ed25519`, `key_ref`, `signed_bytes_ref` exactly the text `dps-signatures 0.2.0 organisation_seal`, `sealed_at`, and `value_b64`. The signed bytes are that profile's, under anchoring 0.2.0's shared rule: `dps-signatures`, `0.2.0`, `organisation_seal`, the key reference, `record`, the entry's `decision_id`, the entry's digest, and `sealed_at`. The digest is the entry's `seal_hash` for an original, and its `derived_digest` for a derived representation: never `derived_from.original_seal_hash`. A verifier that read the original seal there would accept the original's signature on the derived entry. The verifier builds the signed bytes from the entry itself, so nothing in the export has to be kept in agreement with the signature, and a signature moved to another entry, made over another digest, or made under another key reference, profile or version fails by construction. Anything other than these exact values fails, as the signatures profile fails an embedded copy that names other values. `sealed_at` is the issuer's statement: it is the stated time for the state of the key, and never time assurance for the record. An entry MAY be unsigned, as before.
7. MUST NOT carry key material as a source of trust. It carries a key reference only.
8. A document this extension reads that names a member twice, at any depth, is not read, as I-JSON (RFC 7493 §2.3) has it: two readers would otherwise read two different exports under one seal, and covered bytes naming `decision_id` twice would be one record to a reader keeping the last member and another to one keeping the first. The reference check reads every document so, its cases, its vectors, the schemas and the record texts included.

Items 2 to 5 are unchanged from 0.1.0, so that the reading of an export by the anchoring and signatures profiles still holds.

## Beside the export

The export carries no seal of itself: a copy inside would need a replacement rule that the signatures profile's own check does not apply, and one seal would verify under one check and fail under the other. Instead, documents that travel beside the export carry it, in the signatures profile's shape:

- **The export's seal.** An export MAY be sealed as a whole by a signatures 0.2.0 `organisation_seal` of kind `export`, in a signatures attachment read beside the export: `sealed.id` is the issuer's own reference for the export, which states no identifier, and `sealed.digest` the SHA-256 of the export's bytes as issued. That profile defines and tests exactly this, so it adds no rule. An entry's signature covers only the key reference, the identifier, the digest and the time; without a seal of the export, someone holding it can remove an entry's signature (the entry then reads as an ordinary unsigned one), add or drop an entry, or mark content as unavailable, and every entry signature still verifies. The export's seal binds the set of entries and their content as issued. A verifier that relies on the set of entries requires the export's seal in its own configuration, and does not accept an export without one.
- **Independent timestamps.** Timestamps over an entry's signature value, and over the export seal's value, travel in the same attachment, as anchoring 0.2.0 timestamp assertions over a signature value, checked exactly as the signatures profile checks them. They sit beside the export, never inside it, so that adding one later never changes the bytes an export seal covers. A timestamp counts for the signature whose value its imprint covers; the subject's naming is a label, and it does not tell apart an original and a derived entry of one record, which the signatures profile names alike (kind `record`, the record's identifier). A subject that names another assertion fails, as that profile has it, and the timestamp then counts for nothing.

## The verifier and its report

A verifier that uses this extension SHALL validate an affirmed-and-sealed record against its original sealed bytes without inserting defaults or rewriting the payload. A later normalization or migration produces an explicitly identified derived representation and preserves the original verification context, subject to the applicable retention policy (§6.4.2).

The verifier also:

- MUST take issuer trust from a trust policy it configured independently, never solely from a key or a checkpoint carried in the same export. The policy is anchoring 0.2.0's (`dps-anchoring-trust-policy`, version `0.2.0`, schema [`../anchoring/schemas/trust-policy.schema.json`](../anchoring/schemas/trust-policy.schema.json)): the issuer's key is in role `organisation`, and the key states are anchoring's, by reference, with `sealed_at` as the stated time. A compromised key counts only with a verified independent timestamp earlier than `revoked_at` over the signature value; with none, the time cannot be established. The verifier MUST refuse a policy that lists one public key under two references, holders or roles, or one reference to two entries, and report the refusal once (`trust_policy`) and consistently: every signature, key state and timestamp that relies on the policy fails with the reason, and the sealed digests are still compared.
- MUST check each entry's statements that sit outside the seal against the covered bytes, where it can read them: `decision_id`, `record_type`, the predecessor references, the seal field handling and `affirmation_record_covered`. Where it cannot read them, it reports them as not checked. A matching seal alone does not show that an entry is the record it names. Where the bytes omit `record_type`, the check reads it as `decision`, as §6.2 says, and does not rewrite the bytes. The report carries `affirmation_record_covered` through, so a reader sees when the affirmation is outside the seal.
- MUST check a signed entry's signature as the signatures profile checks a seal: build the signed bytes from the entry, verify them with the policy's key for `key_ref`, in role `organisation`, with the pinned certificate holding the key when there is one, and report the key's state when it signed. It MUST report the signature as one dimension (`cryptographic_verification.signature`), verified only when the signature and the key's state are, naming the key reference, the algorithm, where the key came from (`trust_policy`), the certificate check, the key state with what its time rests on, and the **holder the policy gives for the key**: the export names no issuer, so a signature made with another organisation's key that the policy also lists verifies as that organisation's, and the reader needs to see whose. An unsigned entry is reported `not_checked`, with the finding that it carries no signature; it is never reported as verified. An entry whose content is unavailable has its signature reported `unavailable`: it covers a digest whose bytes the verifier does not hold.
- MUST give exactly one entry result for each export entry. The report states the export's entry count, and each entry result names the index of its export entry and the `decision_id` that entry states. Each index from 0 to the count minus 1 appears once. JSON Schema cannot compare two documents, so a reader holding both checks this; the test runner does.
- MUST report these separately: structural validity, cryptographic verification (the seal digest and the signature, each on its own), object-link verification, time assurance, identity assurance, content availability, and the scope of its conclusion. It MUST NOT merge them into one pass, fail or compliance result. The report schema has no place for one.
- MUST keep what it did not or could not check explicit (`not_checked`, `not_supported`, `unavailable`). A report may say less than the reference check (a signature it did not check); it may not say more.
- MUST say where the value it compared a seal with came from. A `seal_hash` carried in the same export shows only that the bytes and the seal agree. It shows that they are the affirmed bytes only if the seal value comes from a source the verifier trusts independently; an entry's verified signature is such a source for the digest, under the trust the policy gives its key.
- MUST report time as verified only against a verified independent timestamp over the entry's signature value, and only where that signature is verified as a dimension (the signature and the key's state when it signed), from the attachment beside the export, and say exactly what it gives: the signature, and so the digest it names, existed no later than T (`no_later_than`, the token's time with its accuracy), by the authority named (`source_ref`) and the timestamp it rests on (`timestamp_index`). Not when the decision was made or affirmed. A timestamp over bytes that are not this entry's verified signature shows nothing about it.
- MUST, where a signatures attachment is read beside the export, report the export's seal (`export_seal`) as the signatures profile reports a seal: its signature, the sealed digest against the export's bytes as received, the key's state, and the holder; and name the attachment's digest (`signatures_attachment_digest`). Where none is read, it reports neither.
- MUST NOT describe a sequence as consistent with a checkpoint without naming that checkpoint. Even a matching checkpoint says nothing about events the issuer never recorded.

**What a verified entry signature shows.** The holder the verifier's own trust policy names for the key issued this digest, under this record's identifier, at a time the key was in use. Where no independent timestamp covers the signature, that time is the issuer's own `sealed_at`: a key listed only as superseded passes on it, so whoever holds a leaked key that the issuer lists only as superseded can backdate; a key that may have leaked is marked compromised, and then only a timestamp earlier than the compromise counts. **What it does not show:** that the record is true, complete or lawful; when it was issued (that is the timestamp's part); that anyone read it; that the record is the latest one (a superseded record keeps a valid signature); that the export is complete, or that the issuer issued these entries together (the export seal's part, and the checkpoint's for a missing tail); or, for a derived entry, that the derived bytes are the affirmed original. The signatures profile's own record check reads only original entries, so a derived entry's signature is checked here, by this extension's check.

## Chains, checkpoints and time

- An export MAY chain its entries: `link(i) = SHA-256(link(i-1) || digest(i))` over the 32-byte raw values, with 32 zero bytes before the first entry. `digest(i)` is the entry's seal, or its derived digest. Each entry carries the previous link, and the chain is checked from its first link. The chain binds the seals and their order, not which record each seal belongs to; the statement check covers that.
- A valid chain shows that the supplied sequence is consistent. It does not show that every event was recorded.
- A missing tail can be detected only against a checkpoint (the count and the last link) established independently of the export. Without one, a correctly linked prefix passes. A checkpoint supplied in or beside the export is not independent, and never supports `consistent_with_independent_checkpoint`. Independent is as [anchoring](../anchoring/) 0.2.0 defines it, under "An independent checkpoint" and "A checkpoint beside the export"; this text adds no definition of its own.
- A report MUST NOT describe a sequence as consistent with a checkpoint without naming that checkpoint. Even a matching checkpoint says nothing about events the issuer never recorded.
- A timestamp the issuer asserts, including `affirmation_record.timestamp` and `sealed_at`, is not independently trusted time, and the actor it names is not independently verified identity. The report records time or identity as verified only against an independent source it names. This extension has no independent source for identity: an organisation's seal binds no person.

## Transformed and unavailable records

- A transformed or re-serialised record MUST keep a link to the original sealed representation, by its original seal, and MUST identify the transformation. It is exported as a derived entry. Its signature, where there is one, signs its derived digest: it shows that the issuer issued that derived representation under the record's identifier, and nothing about the affirmed original.
- Re-hashing a derived representation does not carry over the original seal. A seal recomputed after a migration (§6.2.3.2) is exported as the derived representation's digest, and the original seal is checked and reported on its own.
- An original that is not available, for example after a redaction event or at the end of its retention period, MUST be reported as unavailable. It is reported neither as verified nor as failed, and its signature is not checked.

## Dependencies

- For a signed entry and for the export's seal, this version rests on two Proposals, each by exact version: signatures 0.2.0 (the organisation seal, its signed bytes, the check of a signature, of a seal and of a timestamp) and anchoring 0.2.0 (the shared signed-bytes rule, the trust policy, the key states, the timestamp assertion). Unsigned use needs neither for its checks. A verifier that reads only unsigned exports still names the trust policy it would use and reports whether it accepts it (`trust_policy`, under anchoring's rule); with nothing signed, that status decides nothing else in the report.
- The Core, the meaning of `seal_hash`, and the reference files do not change.
- The reference check in `tests/run_checks.py` loads the signatures extension's own runner for the signature, key-state, timestamp and seal checks, so that the two cannot drift; it needs that runner's requirements (`tests/requirements.txt`).

- **Digest cases** use SHA-256 over exact bytes: a changed payload is detected; a changed record re-sealed in the same export matches that seal but not the original one; JSON that is equal but re-indented, or has sorted keys, does not match the sealed bytes; inserting a default `record_type` breaks the match; the zeroed seal field is handled exactly; a derived representation's digest is its own, not the original's seal.
- **Chain cases**: a middle omission and a reordering are detected, with the derived entry as a fourth link. A missing tail passes without a checkpoint, and the runner says so; it fails against an independent checkpoint.
- **Statement cases** run the reference check over the covered bytes. Unavailable or unreadable bytes give "not checked", and so do covered bytes naming `decision_id` twice, sealed as written: the seal matches, and the statements are not checked, where a reader keeping the last member would have verified them. - **Signature cases** run the reference check of one entry's signature. - **Export seal cases** run the reference check of the export's seal: verified with its timestamp and without; nothing beside the export; an entry's signature removed, content made unavailable or an entry added after sealing, each failing the sealed digest; a key the policy does not list; the export with the derived entry sealed as issued; a refused policy; the seal presented under another reference.
- **Pairing cases** read a report with its export, the attachment beside it and the policy. They detect a missing entry, a duplicated entry, an entry count lowered to hide one, a relabelled result, a relabelled export entry reported with verified statements and signature (and accept it reported as it is), an export digest or attachment digest that is not the document's, an unsigned export reported as signed, an unsigned entry reported as signed, a signature by an unlisted key reported verified, a holder that is not the policy's, time or a key state resting on a timestamp that was not read, an export seal reported verified after the export changed or where nothing was read, a refused policy reported accepted, and identity reported verified; and they accept a report that says less than it could.

## Changes from 0.2.0

For anyone who implemented the 0.2.0 text (#53, #55, #58 and the sentence #59 added, as they stood at `49a6d9b`).

**What 0.2.0 allowed and 0.3.0 refuses:** a report that calls time verified next to an entry signature that is not verified. Under 0.2.0, the reference check gave a time wherever the signature itself verified over its bytes, even when the key's state then failed: a compromised key whose only timestamp is after the compromise (G18), or a superseded key whose only timestamp is after it was superseded (G35), had their signature failed and their time verified, and the text ("over the entry's signature value") allowed that reading. 0.3.0 takes the dimension: time is verified only where the entry's signature is verified, signature and key state, and the report schema refuses the other reading (P56). The key state's own finding says why it failed and, for a compromised key, names the timestamp's time it compared; the entry gets no time either way. One sentence is added, which refuses nothing: "independent", for a checkpoint, is as anchoring 0.2.0 defines it, so that the point that a checkpoint in or beside the export is not independent rests on this text and on anchoring's, as said on #59. Nothing else changes: the export, its rules, the entry's signature and its signed bytes are those of 0.2.0.

**A 0.3.0 verifier and a 0.2.0 document.** The schemas pin `profile_version` to `0.3.0`, so a 0.2.0 export or report is not valid input to this version's check. An export's content is the same under both, and an entry's signature does not name portable verification's version, so the same export labelled `0.3.0` is valid and its signatures verify unchanged; an export seal, which covers the export's bytes, the label included, has to be made again. A 0.2.0 report stays a 0.2.0 report, read by the 0.2.0 text and check as they stood at `49a6d9b`.

## Changes from 0.1.0

For anyone who implemented the 0.1.0 text (#21, as it stood at `d6c802e`). The rule agreed on #28 asks whether a change makes documents valid under the published text invalid; the suite does, so the version moves.

**What 0.1.0 allowed and 0.2.0 refuses:**

- A signed entry made another way: another suite, other signed bytes, no `sealed_at`. 0.1.0 said that the signed bytes SHOULD include the profile, its version and the key reference, and that the SHOULD would become a MUST once a suite was chosen (#45). It is chosen: the signatures 0.2.0 organisation seal, `algorithm` and `signed_bytes_ref` as fixed values, `sealed_at` required and signed. An entry signed otherwise fails at `cryptographic_verification.signature`, and its member is not valid against the export schema.
- A document this extension reads that names a member twice, at any depth. It is not read.
- A report that does not say whether the trust policy was accepted; that calls a signature verified without naming its key reference, algorithm, holder or key state, or with a key state that is not verified; that calls a key state verified without its key reference, time basis or time; that calls time verified without saying by when the signature existed, or rests a time on a timestamp it does not name; that calls a compromised key verified on the stated time; or that calls the export's seal verified without its holder or with a failed sealed digest.

**Other changes, which refuse nothing a correct 0.1.0 document stated:** the export MAY be sealed as a whole and timestamped by documents beside it; the report's signature dimension names the holder, the certificate check and the key state; `time_assurance` carries `no_later_than` and `timestamp_index`; `export_seal` and `signatures_attachment_digest` are added; the trust policy is anchoring 0.2.0's by reference; the written-against release moves to Core v1.3 rev. 11 and reference files 5.2.0, under which the fields read are the same. An unsigned entry, and an unsigned export, are exactly as valid as before.

**A 0.2.0 verifier and a 0.1.0 document.** The 0.2.0 schemas pinned `profile_version` to `0.2.0`, so a 0.1.0 export or report was not valid input to the 0.2.0 check, and the check did not read it; the 0.3.0 schemas pin `0.3.0`, with the same effect. A 0.1.0 export stays a 0.1.0 export, checked by the 0.1.0 text and check as they stood at `d6c802e`. The same content labelled `0.2.0` was a valid 0.2.0 export when its entries were unsigned, since items 2 to 5 do not change, and labelled `0.3.0` it is a valid 0.3.0 export on the same condition; a signed 0.1.0 entry has to be signed again under the suite.
